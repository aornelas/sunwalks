Architecture: the Claude layer

The README covers the calendar itself. This page covers what sits on top of it: the photo-source interface, vision tagging, the forecast record they're compared against, the engine that turns all three into a plan for tomorrow's walk, and the Telegram walk buddy that delivers the plan and collects what happened. The MCP server on the roadmap is a second way to reach the same engine.

Place is the one piece of metadata the app writes. The Picker API gives no GPS, so a place comes from the owner, or from a Claude suggestion the owner confirms. Choices worth knowing about

Structured outputs, not forced tool use

The request sets output_config.format to a JSON schema, so decoding is constrained (forced tool_choice returns a 400 on Claude Opus 5.5 anyway). The schema is generated from Zod with unsupported keywords (ranges, lengths, patterns) removed; Zod then validates every response, so those limits still hold. zodOutputFormat isn't used because it turns enums into descriptions, dropping the category constraint.

Versioned prompts

Each prompt is a file under prompts/, and every tag row records the version that produced it. Bumping TAG_PROMPT_VERSION makes every photo pending again, so the next run re-tags the archive.

Prompt caching

The prompt and the list of known places come first in the system prompt and carry the cache breakpoint; the photo comes after. Every request after the first reads that ~2,200-token prefix from cache.

Files API

Each photo is uploaded once and its file_id stored on photos.claude_file_id, so re-tagging doesn't resend bytes. Uploaded files stay in the Anthropic account until deleted.

Low effort

Reading a sky is perception rather than long reasoning, so requests run at effort: "low". Most output tokens are still thinking, so output dominates the cost.

No refusal fallback

Server-side fallbacks would re-run a refused request on another model, but the Batches API rejects the parameter. A refusal is logged and the photo stays pending.

Running it

npm run tag-photos tags every photo that has no tags at the current prompt version. By default it submits one Message Batch (half price, usually done within the hour), stores the batch id in tagging_batches, and polls it. Interrupting it is safe: the next run resumes the unfinished batch instead of submitting a new one.

FlagEffect
(default)One Message Batch, resumable

With nothing left to tag, a run makes no API calls. Every run prints its token use: requests, how many hit the cache, and uncached input, cache reads, cache writes and output. Each tag row also keeps its own counts.

The forecast record

forecast_days is a cache: one row per date, overwritten on every fetch, so by morning the evening-before forecast is gone. forecast_snapshots keeps it, one row per (date, lead time, source):

live

From every forecast fetch

lead_days is the number of owner-local days between the fetch and the morning, so lead 1 is the forecast as it stood the day before. A later fetch on the same day replaces the row, so lead 1 ends up holding the last forecast issued that evening. The nightly cron (/api/cron/forecast, scheduled in vercel.json) makes sure that fetch happens even if the app isn't opened.

historical

Rebuilt by backfill

npm run backfill-forecasts rebuilds these from Open-Meteo's Historical Forecast API, so calibration can start with the whole archive. These are lead 0: the archive is stitched from the first hours of each model run. The Previous Runs API has true day-ahead values, but lacks the low/mid/high cloud split and visibility the verdict rules need.

Snapshots store the forecast inputs as well as the verdict. Calibration should re-derive the verdict from the inputs, as the planning view already does, so a rule change applies to the whole history.

The engine

The engine turns the forecast, the tagged photos and the walk log into a plan for tomorrow. It splits the work in two: plain TypeScript does the counting, and Claude does the judgement.

Database table Plain TypeScript Claude API Script / job

What plain code does

mornings.ts

Joins everything known about each morning: the forecast (the evening-before live snapshot when there is one, else the historical one, with the verdict re-derived from its inputs), the sky the day's photo shows, and the walk log entry.

calibration.ts

Counts how often each forecast category matched the sky in the photo. Confidence is the smoothed held-rate (held + 1) / (forecasts + 2), so a category with no history reads 0.5, not 0 or 1. It also gives the odds of each sky given a forecast.

place-scores.ts

Scores each morning 0–1 from your rating, the only signal that says the place paid off (drama mostly measures the sky, so it only stands in without a rating), averaged per spot and observed sky and shrunk towards a default for the spot's kind. Home is scored like a spot. A spot's rank is its expected score across the skies the forecast tends to bring.

reach.ts + schedule.ts

Which spots fit a morning: sunrise, plus how long you stay, plus any walk there, plus the trip home, against when you must be back. Weekly rules ("school days, back by 7:50, 5 minutes") and dated exceptions (holidays, summer break) set the deadline.

Defaults by kind, until walks say otherwise: high places for colour, forest for fog, a short walk for a clear sky, home for rain. They're capped at 0.75, so a few genuinely great mornings somewhere can outrank an untried spot that merely suits the sky on paper.

npm run calibration prints all of this: the backtest (how often each forecast held, and the full forecast-against-observed table), the place scores, and the filed preferences. It makes no API calls.

What Claude does

Planning

recommend.ts, prompt in prompts/recommend-walk/v2.md. Claude reads the owner's preferences through the memory tool, calls the four engine tools, and decides: stated preferences first, then the ranking, then specific past mornings. The answer is structured output, validated, and its spots must be real ones.

Filing feedback

feedback.ts, prompt in prompts/file-feedback/v1.md. Claude reads the existing preferences and edits them with the memory tool, adding, sharpening or replacing rules instead of appending.

Honest backtests

Planning a past date uses only the mornings before it, and answers get_forecast from what was forecast at the time, so the recommender itself can be tested against history.

ToolGives Claude
get_forecastThe morning's category, reason, sunrise, cloud by level, rain and fog chance, ceiling
forecast_accuracyHow often that category has held ("7 of 9 Foggy forecasts held"), its confidence, and what the sky was instead
spots_forSpots (and Home) ranked for the forecast, split into in reach and out of reach for that morning's schedule, with walks logged and notes
similar_morningsPast mornings with the same forecast: the actual sky, where the owner went, rating, note, drama

The tool loop

Both run through tool-loop.ts, a manual loop written out on purpose as a teaching example:

  1. Send the conversation, with the tools Claude may call.
  2. Run every tool_use Claude asks for, in our own code, and return all the results in one message. A failing tool goes back as an error result instead of ending the run.
  3. Repeat until Claude stops asking for tools; its last message is the answer. The loop gives up after 12 turns.

The custom tools use strict: true, so their inputs always match their schemas. The memory tool (memory_20250818) is client-side: Claude issues file commands and memory-store.ts carries them out.

The walk buddy (Telegram)

The walk buddy is the engine's daily surface: a private chat with your own Telegram bot, run from the Vercel app through the Bot API, so it works without a laptop or a Claude Code session.

Telegram Script / job Plain TypeScript Claude API Database table

The morning report is a photo, a place and a 1–5 rating, every morning. A morning at home counts: a window photo on a wet day, place Home. That's how calibration sees the skies on days nobody goes out, and how the engine learns when staying in was right. The rating asks whether the choice paid off: 5 exactly right, 4 glad I went (or stayed), 3 fine, 2 somewhere else would have been better, 1 the wrong call.

The evening plan

/api/cron/evening-plan sends the plan as text: a suggestion, not a question. It only suggests spots you can get back from in time, and says when a farther one opens up (a weekend, a holiday, an earlier sunrise).

A photo

Filed, tagged and acknowledged. With words, Claude logs what they say; without, the code asks. Then buttons ask for whatever is missing: the place (last night's picks first, Home last), then the rating. Each tap edits the same message. Only an album's first photo asks.

Late photos

An image sent as a file keeps its EXIF, so it's filed on the morning it was taken. A normal photo goes on the day it was sent, unless the words name another morning ("this is from Tuesday", up to 14 days back), and moves with the report. Stored copies keep no metadata, GPS included.

No report isn't a sleep-in

/api/cron/morning-nudge asks for the photo only if nothing came in, with a Slept in button. An unanswered nudge leaves the morning unreported, and a sunrise photo later clears a mistaken Slept in.

The conversation

Telegram gives a bot no history, so chat_messages keeps both sides. The last six hours go ahead of each message to Claude, so "12" after "how long home from St. Mary's?" lands with its question. Photos picked in the web app count as the morning's photo, and an import of today's or yesterday's gets the usual buttons.

Spots and the schedule

Kept from the chat: "McLaren is a 10 minute drive and a 15 minute walk", "no school on Nov 11", "summer break June 12 to August 20". Prompt in prompts/walk-buddy/v3.md. /spots and /schedule list what's on file without a Claude call.

The weekly summary

/api/cron/weekly-summary counts the last seven mornings: out, home, slept in and unreported, ratings, the best one, how often forecasts held, and which preferences changed. /plan and /week work on demand.

Trust

The webhook rejects any request without the secret given to setWebhook (Telegram echoes it in X-Telegram-Bot-Api-Secret-Token; compared in constant time), then drops updates from any chat but TELEGRAM_CHAT_ID with an empty 200. Past those checks the text still isn't trusted: Claude gets it fenced as your account of your mornings, and the code checks every value its tools pass (dates, ratings, spot names, timings, schedule times).

Telegram redelivers an update when the webhook is slow, so the route records each update_id in telegram_updates before doing anything, and a second copy is a no-op. The same row records the update's kind, its album, any error (also sent to the chat as "That didn't work: …") and the tokens it cost.

Running it

  1. Create a bot with @BotFather and set TELEGRAM_BOT_TOKEN.
  2. Send it /start from your phone, then run npm run telegram -- chats to find TELEGRAM_CHAT_ID.
  3. Set TELEGRAM_WEBHOOK_SECRET (openssl rand -hex 32) and, with SITE_URL pointing at the deployment, run npm run telegram -- set-webhook. -- info shows the webhook Telegram has on file and its last delivery error.
  4. Set the spots' timings and your schedule, from the chat or with npm run walk -- timing and -- schedule-add. npm run walk -- reach shows which spots fit a morning.

npm run telegram -- plan, -- nudge and -- week send those now. TELEGRAM_API_BASE points the client somewhere else, which is how it was tested: against a stand-in Bot API that logged every call.

Not built yet

  • Nothing tags photos imported from Google Photos as they arrive. Run npm run tag-photos after an import; photos sent to the walk buddy are tagged on arrival.
  • There's no UI in the app to set or confirm a place, log a walk or add a spot; the walk buddy and npm run walk do it until the MCP server does.
  • Photos imported from Google Photos are joined to the walk log by date; only photos sent to the walk buddy get a place from the report.
  • A spot's timing is one number per leg, not per day: traffic and parking aren't modelled.
