Message threads in the tool loop

What Claude's message-threads beta did for the Sunwalks agent loop when measured, why it stays off, and what was built to find out.

Threads stay off. On the planning loop, a thread cut the request size of turns 2 and 3 by 62–80%. Response time didn't change beyond noise, and token use and plan quality were the same. The code is in place behind CLAUDE_MESSAGE_THREADS and costs nothing while unset.

Phase 3 results

Measured on 20 Nov 2026. Ten mornings, 12–21 Nov, were each planned twice with recommendWalk on Claude Opus 5.5: once with threads off and once with them on, alternating which ran first. The runs read the production database with nothing written: no plan was stored and memory was read-only. All 20 plans passed the schema check. Total spend was $0.68.

Why it stays off

  • No noticeable benefit here. Apart from the smaller requests on turns 2 and 3, nothing measurable changed. A thread saves re-uploading and re-processing the conversation, and the planning loop has very little of it: 3 turns over about 10 KB. Most of each turn's time is the model writing its reply, which a thread doesn't touch.
  • The quoted 35% belongs to a different workload. Roy Arsan (Applied AI team, as recalled) cited a 35% latency saving in the Anthropic webinar "Build Agents with Claude Platform on Google Cloud". Anthropic's docs give no figure, saying only that time to first token "stays lower and steadier as the conversation grows". A long loop with a large history fits that description much better than this one.
  • It costs something to turn on. Threads are a beta, and they aren't covered by zero data retention (ZDR): Anthropic holds a thread's conversation in memory for up to an hour. Turning them on would also rule out compaction and most context editing. With no gain to show, none of that is worth taking on.
  • Keeping the code costs nothing. With the flag unset the loop behaves as before. The request trace it adds stays useful. If a loop grows to many turns or large tool results, the flag and the A/B script make it a quick test.

How message threads work

Beta header message-threads-2026-08-12, on an ordinary POST /v1/messages.

  • Create: the first request as usual (full messages, system, tools) plus thread: {type: "create"}. The API stores the conversation under the response id.
  • Continue: only the new messages plus thread: {type: "continue", previous_message_id}, and no system or tools.
  • Replay: threads are best-effort. On 404 thread_not_found, the full conversation goes out again as a new create. The SDK helper (client.beta.messages.thread(), in @anthropic-ai/sdk 1.2.0 and later) does this for you.
  • Lifetime: a thread expires 5 minutes after its last request and is deleted within 1 hour of its last use.
  • Fixed for the thread's life: model, tool_choice, thinking, output_config, context_management, top-level cache_control, and the set of beta headers. A change returns 400 thread_fingerprint_mismatch.
  • Price and caching: pricing and rate limits are the same, and a thread caches nothing, so prompt caching still matters.
  • Can't be used with: Message Batches, token counting, compaction, most context editing, or organizations with HIPAA readiness enabled. Not available on Bedrock or Vertex AI.

Source: platform.claude.com, Message threads, read 20 Nov 2026.

Every agent call goes through one manual loop, src/lib/tool-loop.ts. It already keeps the model, system prompt, tools and output settings the same on every turn, and only adds to the history, which is all a thread asks for.

What was built

Request tracing

src/lib/claude-client.ts adds createClaudeClient(), which every entry point except photo tagging now uses. Its fetch notes each request's size, time to response headers, status, and whether it was a thread create or continue. The loop collects these per turn with traceRequests, returns them as trace, and logs one [tool-loop] line per run. A turn after the first with two requests means the conversation was replayed.

The thread path

With the flag on (CLAUDE_MESSAGE_THREADS=1 or thread: true), runToolLoop creates a thread with the SDK helper and sends each turn with thread.send(). It keeps its own copy of the history either way. The helper is created with unsupportedRequestBehavior: "continue_unthreaded", so a request the API won't thread finishes without one. The loop stays manual, as its header comment intends.

const thread = client.beta.messages.thread({
  model, max_tokens: 16000, system, tools: toolDefs,
  cache_control: { type: "ephemeral" },
  output_config: { effort, ...(outputFormat ? { format: outputFormat } : {}) },
  unsupportedRequestBehavior: "continue_unthreaded",
});
const response = await thread.send(next); // turn 1 creates, later turns continue

Dry runs

recommendWalk(client, date, onToolCall, { dryRun: true }) doesn't store the plan. It passes memory: "read-only" to the loop, which turns down every memory command except view before it reaches the database.

Tests

test/engine.test.mts drives a real SDK client over a scripted fetch, so the SDK's own thread code runs. It covers continue requests carrying only the new messages with the fixed fields unchanged, a lost thread being replayed in full, an unthreadable request finishing without a thread, and read-only memory.

Re-running the measurement

npm run threads-ab -- --runs 10 --out results.json

Each morning is planned once per arm, going back a day at a time from --date (default: the next morning to plan). The runs are dry and write nothing, and each one costs about $0.03–0.05 on Claude Opus 5.5. The summary gives, per arm, the time and request size of the turns after the first, replays, tokens and cost.
